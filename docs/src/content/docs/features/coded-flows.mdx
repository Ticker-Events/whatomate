Coded flows are conversations written in Go and shipped in the binary. An admin assigns the keywords that start one and can turn it on or off. The steps cannot be edited in the flow builder.

Visual flows under **Chatbot → Flows** are a graph stored in the database. A coded flow is a function. The outline shown in **Chatbot → Coded flows** is a label list for people. The function is what runs.

The flow that ships today is **TiQR Ecommerce** (`tiqr_ecommerce`). It loads a TiQR store, then lets the customer buy for store pickup, check an order, or talk to an agent.

## Turning a flow on

<Steps>

1. Open **Chatbot → Coded flows**.
2. Pick the WhatsApp account. Keywords belong to that account.
3. Enter keywords separated by commas. A message starts the flow when it contains one of them. Matching ignores case. Blank keywords are dropped. A keyword longer than 200 characters is rejected. Duplicates that differ only by case are stored once.
4. Turn the flow on and save.

</Steps>

Saving needs the `flows.chatbot` write permission. Listing and preview need read. A new binding is off until someone enables it.

If a visual flow uses the same keyword, the coded flow starts. An empty keyword list never matches. A disabled binding never matches. The check is limited to the organization and the WhatsApp account on the inbound message.

The message that contains the keyword is the trigger. It is not treated as the customer's answer to the first question.

## How a turn runs

Every inbound message runs the flow function from the top. Finished calls return the result they saved last time. They do not send the message again and they do not call the store again. The first call that is still waiting sends the next prompt, or accepts the reply that just arrived, and then the function returns.

That is why the function can be straight-line Go, including loops, and still pause between WhatsApp messages.

The session stores the log in `SessionData._coded_calls`. Each entry records the call name and whether it succeeded. A choice also stores the button or row id. A store call stores the payload. On the next message the function walks that log in order. Call order is the identity of a step. Inserting, removing, or reordering a call in the middle of a function changes what an in-progress session replays.

While a coded flow is active the session has:

| Field | Meaning |
| --- | --- |
| `SessionData._coded_flow` | Flow key, for example `tiqr_ecommerce` |
| `CurrentFlowID` | Left empty so the visual graph runner does not take the session |
| `CurrentStep` | Name of the call that is waiting for a reply |
| `Status` | `active` until the flow ends or transfers |

An active coded flow is resumed before commerce checkout, cart quantity, keyword rules, and visual flows. A WhatsApp Flow submission in the middle of a coded flow stays inside that flow.

When the flow ends or transfers, `_coded_flow` is cleared, `CurrentStep` is cleared, and the session is marked completed.

### What the function can do

The flow is a `func(*Conv) error`. These calls are the whole API.

| Call | What it does the first time | What a later message does |
| --- | --- | --- |
| `Say` | Sends one text message | Skips it |
| `AskButtons` | Sends reply buttons and waits | Accepts a button from that prompt |
| `AskList` | Sends a list built from items and waits | Accepts a row id from that list |
| `AskCarousel` | Sends a product carousel and waits | Accepts a product id from those cards |
| `AskImageButtons` | Sends reply buttons with an image header | Accepts a button from that prompt |
| `AskNumber` | Sends the prompt and waits for text | Accepts text that matches the pattern, or a confident AI-normalized value that matches |
| `AskLocation` | Sends a WhatsApp location request and waits | Accepts a location pin (latitude / longitude JSON) |
| `AskFlow` | Opens a WhatsApp Flow and waits | Accepts the form submission |
| `Store` | Calls one TiQR REST operation and saves the object | Returns the saved object |
| `StoreMCP` | Calls one TiQR MCP operation and saves the object | Returns the saved object |
| `StoreList` | Calls a list operation and saves `results` | Returns the saved list |
| `LookupOrder` | Loads the latest order for this phone through TiQR MCP | Returns the saved order |
| `Once` | Runs a function one time, such as appending the cart | Skips it |
| `Transfer` | Tells the customer, queues an agent transfer, and ends | Already ended |
| `End` | Marks the session completed | Already ended |

A call that returns `false` means the function should return now. The customer has not answered yet, the answer was routed to a guide question or an agent, or the call failed. A call that returns `true` means the function can continue in the same turn.

`Store` and `StoreList` read the TiQR REST base URL and store id from the chatbot settings for that WhatsApp account (`CommerceRESTURL`, `CommerceStoreID`). `LookupOrder` does not use those REST operations. It calls TiQR MCP `lookup_order_status` with the store id and the customer's WhatsApp number.

Placeholder strings such as `{{option_name}}` and `{{tiqr_cart}}` are filled from `SessionData` before a message is sent or a store call is made.

### Which reply counts

Reply buttons, list rows, and carousel cards accept an answer in two ways:

- The button or row id matches after trimming spaces.
- The message text matches the title, ignoring case.

Ids stay in English. Titles are what the customer sees. A button id that was not offered on this step is not a request for an agent. The same choices are shown again.

Every customer question carries a short step note (`Doing` and `Expect`) so the intent role knows what the step is for. The intent prompt also includes the question that was just shown, the allowed choice ids with their labels (for carousels, the card body plus the button title), and, for number steps, the pattern a normalized answer must match.

Free text that is not one of those titles leaves the script. So does a number that fails `AskNumber`, and so does text sent while a WhatsApp Flow is waiting. The flow asks the intent role (text-only AI, no catalog tools) to map the message onto one route:

```json
{"language":"en","route":"unclear","choice_id":"","collection_id":"","product_query":"","answer":"","confidence":0}
```

| Route | Meaning |
| --- | --- |
| `choice` | `choice_id` must be one of the ids on this step (including a typo of a title) |
| `collection` | `collection_id` must already be in the loaded collections (menu and collection steps only) |
| `product` | `product_query` is a short search string; no id is accepted |
| `answer` | Normalized free-text value for this step (for example `"Two"` → `"2"`); must match the step pattern; no ids |
| `checkout` | Customer wants to place the order with the current cart; no ids |
| `handoff` | Transfer to an agent (human/staff request, confused customer, or inventing catalog data) |
| `unclear` | Ask one clarifying question and stay on the step |

Go checks every id against an allow-list. An invented id, a product route that also fills an id, an answer that fails the pattern, or JSON that is not this contract transfers immediately. Confidence defaults to a threshold of `0.75`. A grounded `choice`, `collection`, `product`, `answer`, or `checkout` at or above the threshold is applied in the same turn. A grounded `unclear` (or a route below the threshold) asks up to three guide questions, then transfers. A button the flow offered, including **Talk to staff**, does not go through this AI step.

`checkout` from free text works on the menu and on any buy step. If `tiqr_cart` is empty, the customer is told the cart is empty and the collection list is shown again. If the cart has lines, the flow opens the checkout WhatsApp Flow and places the order the same way as the Checkout button.

Language, translation, guide, and recover questions are separate roles so each can later use a different model. Provider `jev` is reserved for the intent role. Today they use the chatbot AI already configured for the account. If AI is not configured, an off-script reply transfers (recover falls back to a canned customer message).

When a TiQR fetch fails (store, collections, products), the recover role writes a short customer message such as “try again later”. WhatsApp never sees URLs, HTTP status text, curl, tokens, or request payloads. When `create_order` fails because customer details are missing, every missing field named in the error is asked one at a time, in a fixed order (name, phone, email, address, city, state, country, pincode, notes). The order is retried only after each of those replies is stored. Retries after the first attempt are controlled by `[codedflow] order_retries` (default `2`).

### Language

The preferred language is stored as `customer_language` only when the intent role returns it on a free-text reply, and only if the session does not already have one. English button taps never call that role, so the language stays empty and messages are sent as written. English (`en` or `en-*`) is also sent as written. Any other label (Hindi, Tamil, Manglish, and so on) is translated before send. `{{placeholders}}`, asterisks, numbers, prices, and line breaks are kept. Translations are cached on the session in `_translations`, so the same line is not translated again on the next turn.

Catalog text is not translated. Collection names, product names, option names, and prices stay as the store sent them. Button titles are limited to 20 characters after translation, list buttons to 20, section titles to 24, and list headers and footers to 60.

### Preview

**Preview** on the coded-flow card runs the same function without sending WhatsApp messages and without creating an agent transfer. The preview session lives in memory for 30 minutes.

Each outbound preview bubble includes a snapshot of session context variables at send time. Intent, guide, and translate calls for that turn are returned as `ai_calls` and attached to the related message (or shown as a debug bubble when no message followed). The sidebar shows the latest full context as a collapsed JSON tree (expand nodes as needed) and the AI calls from the last turn, with copy buttons for both.

### Production tracing (SignOz)

Live coded-flow turns emit structured logs when tracing is enabled (default **on**). Set `WHATOMATE_CODEDFLOW_TRACE=false` (or `0` / `off` / `no`) to disable. You can also set `[codedflow] trace` in `config.toml`; the env var wins when present.

Every line uses message `coded_flow.<event>` and attributes:

| Attribute | Purpose |
| --- | --- |
| `component` | Always `coded_flow` — primary SignOz filter |
| `event` | `inbound`, `turn_context`, `whatsapp_outbound`, `ai_request`, `ai_response`, `tiqr_request`, `tiqr_response` |
| `session_id`, `org_id`, `account`, `phone`, `flow_key`, `step` | Correlate a conversation |
| `prompt` / `response` | AI input and output (`ai_role` is `intent`, `guide`, or `translate`) |
| `curl` | Reconstructable TiQR REST call |
| `params_json` / `response_json` / `context_json` | Bodies (truncated when very large) |
| `message_body` | WhatsApp text or interactive body that was sent |

Example SignOz filters:

- `attributes.component = "coded_flow"`
- `attributes.event = "ai_response" AND attributes.ai_role = "intent"`
- `attributes.event = "tiqr_request" AND attributes.operation = "search_products"`
- `attributes.session_id = "<uuid>"`

Preview / mock runs do not write these production traces.

**Mock TiQR responses** is on by default. Each store or order lookup stops and asks for a JSON object instead of calling TiQR. Turn it off before **Start** to call the real store. In that mode checkout can place a real order.

The customer phone in the preview is used when the flow looks up an order. The default is `910000000000`.

## TiQR Ecommerce

Key: `tiqr_ecommerce`.

The customer can buy products for pickup or delivery (when the store supports it), check the latest order on their phone number, or talk to an agent. Customer details at checkout are collected with WhatsApp Flow `1557965846018132`. That flow has to exist in Whatomate under the same Meta flow id, so the form can open on its first screen.

The outline in the admin UI is:

1. Load store and collections
2. Buy, order status, or agent
3. Add items and check out
4. Check order status
5. Talk to an agent

```text
keyword
  → get_store
  → list_collections (limit 20)
  → menu
       ├─ Buy products → fulfillment → collection → products → cart → checkout → end
       ├─ Check order status → latest order for this phone → end
       ├─ Talk to staff → transfer
       ├─ free text → collection id → products → …
       └─ free text → product search → products → …
```

If the store cannot be loaded, or it has no collections, the customer gets the thank-you message and the flow ends. Those failed calls stay failed for the rest of the session. The next message replays them and does not retry TiQR.

### Menu

When the store has a name, the menu is:

```text
Welcome to {store name}.

What would you like to do?
```

Without a name, the first line is omitted. The buttons are:

| Id | Title |
| --- | --- |
| `buy_products` | Buy products |
| `check_order_status` | Check order status |
| `talk_to_agent` | Talk to staff |

`talk_to_agent` transfers immediately. It does not ask the AI. Free text that asks for a human, agent, or staff, or a confused customer, transfers from whatever step they are on.

### Fulfillment

Before the collection list, Buy products reads `delivery_modes` from the store already loaded by `get_store`.

| `delivery_modes` | What the customer sees |
| --- | --- |
| Missing or empty | No extra prompt. `delivery_mode` is stored as `PICKUP_FROM_STORE` and browsing continues (same as before). |
| Only `PICKUP_FROM_STORE` | Explains that the store is pickup only, with a **Proceed** button. |
| Both pickup and delivery | Reply buttons **Store pickup** and **Delivery**. The choice is stored as `delivery_mode`. |
| Only `DELIVERY_TO_LOCATION` | Asks for a WhatsApp location pin immediately. |

When delivery is selected (or is the only mode):

1. The flow sends a WhatsApp location request.
2. It calculates distance locally from the store’s `latitude` / `longitude` and compares against `free_delivery_radius` and `delivery_radius` (same rules as TiQR `evaluate_delivery`). No MCP call.
3. For `free` or `paid`, it tells the customer the result and shows the store’s free and paid radii, then continues to collections.
4. For out of range when pickup is also supported, it shows the out-of-range copy and buttons to switch to **Store pickup** or **Share again**.
5. For out of range when delivery is the only mode, it shows the same radii without offering pickup, then asks for another pin.

Each pin attempt uses its own call names (`delivery_location_1`, `delivery_check_1`, …). Latitude and longitude are stored as `delivery_latitude` / `delivery_longitude` for the order.

### Buying

Buying is a loop. The customer can add more than one item before checkout. Store and collection data from the opening calls are reused. They are not fetched again when the customer adds another item.

<Steps>

1. **Fulfillment.** Delivery mode and, when needed, a location pin (see above).
2. **Collection.** The customer gets a list titled "Our collections". The button is "Browse". Each row uses the collection `name` as the title and `description` as the description. The chosen row saves `collection_id` from `id` and `collection_name` from `title`. Free text on this step can also route to a loaded collection id, or to `search_products` with a product query. An empty search result tells the customer the item is not in the store and returns to the collection list. The model never invents product rows.
3. **Products.** `list_products` is called with `category_id` set to that collection id, or `search_products` with the validated query. Two or more products are a carousel. The card text is `{name} (₹{min_price})`. The image is `images[0].original_url`. A product with no image uses a built-in fallback photo. The card button is "Add to cart". One product cannot use a carousel (WhatsApp needs at least two cards), so it is an image reply instead: the product image as the header, `*{name}* (₹{min_price})` plus the product description as the body, and an "Add to cart" button. Either tap saves `product_id` and the product `options` array, and also `product_selected`.
4. **Option.** What happens next depends on how many options the product has.
5. **Quantity.** The customer replies with a whole number of 1 or more. The pattern is `^[1-9][0-9]*$`.
6. **Collection fields.** Required fields on that collection are asked one at a time before the line is added. See below.
7. **Cart line.** The option, quantity, and any collection answers are saved once. A replay does not add the line again.
8. **Next.** The customer chooses "Add more items", "Edit cart", or "Checkout".

</Steps>

Option handling:

| Options on the product | What the customer sees |
| --- | --- |
| None | "Sorry, this item isn't available right now." The flow still asks whether to add something else or check out. Nothing is added. |
| One | That option is selected. No extra list. The flow asks for a quantity. `option_id` and `option_name` are set from that option. |
| More than one | A list titled "Choose an option". Each row is `{name} (₹{price})`. The choice saves `option_id` and `option_name`. Then the flow asks for a quantity. |

The quantity prompt is: "How many *{option name}* would you like?" A reply of digits that match `^[1-9][0-9]*$` is accepted immediately. A reply such as "Two" is scored by the intent role; when it returns `route: answer` with `answer: "2"` at or above the confidence threshold, the cart uses `2` in the same turn. A reply that stays unclear is guided on this step and the cart is not changed.

A valid quantity does not add the line yet when the collection has required capture fields. Those fields come from `required_capture_fields` on the collection. The product's category is used when it matches a loaded collection. Otherwise the selected collection is used.

Each required field is a separate question. The question is the field label, then its help text, then the allowed options when it has any. A number field must be numeric. A single-select or multi-select answer must be one of the options (multi-select is comma-separated). Any other required field accepts a non-empty reply. An answer that does not match is asked again, and nothing is added. Optional fields are not asked.

The answers are saved on the cart line and on the session. The same option with the same answers increases the quantity. The same option with a different answer is a second line. The cart summary shows each answer under its label.

A collection with no required fields skips the questions. The saved line includes the answers when any were asked:

```json
{
  "product_option": "9",
  "quantity": "2",
  "product_name": "Normal Cake",
  "option_name": "Vancho",
  "capture_fields": { "writing": "Happy Birthday Aswin" },
  "capture_labels": { "writing": "Writing on Cake" },
  "capture_order": ["writing"]
}
```

`capture_fields` is omitted when the collection did not ask anything. `tiqr_cart` is the list of those lines. `cart_count` is the sum of quantities. The customer then sees the option name, the cart summary (including collection answers), and how many units are in the cart.

"Add more items" returns to the collection list. "Checkout" leaves the loop. Free text such as “checkout” or “place my order” on any buy step also enters checkout when the cart has lines. An empty cart gets a short message and the collection list again.

If `list_products` or `search_products` fails, the customer gets a safe “try later” message (never the raw API error) and returns to the collection list. An empty product list uses the “couldn’t find that” copy and also returns to collections.

### Checkout

Checkout opens WhatsApp Flow `1557965846018132` with the button "Enter details". The form asks for the name, phone number, and address used to place the order. The body mentions pickup or delivery based on the stored `delivery_mode`. Text sent instead of the form is an off-script reply. The form's fields are copied onto the session under the field names the flow submits.

The order is placed with `create_order` only after that form is submitted. Each order field is read from the session value the form stored:

| Order field | Session value |
| --- | --- |
| `email` | `customer_email`, or `email` when that value contains an `@`. A phone number in either field is not sent as the email. |
| `items` | `tiqr_cart` |
| `notes` | `customer_notes` when no collection answers were captured. Otherwise plain text per cart line: `{product_name}({option_name})` then `- {label}: {value}`, with an optional trailing `Note: {customer note}` |
| `delivery_mode` | Session `delivery_mode` from fulfillment (`PICKUP_FROM_STORE` or `DELIVERY_TO_LOCATION`). Empty defaults to pickup. |
| `new_address` | The address object below. Delivery also includes `latitude` and `longitude` from the pin, rounded to 6 decimal places |
| `buyer_meta_data` | `name`, `email`, `phone`, `phone_number`, and `notes` when set. Delivery also includes `latitude` / `longitude` from the pin (`delivery_latitude` / `delivery_longitude`) |
| `phone_number` | The WhatsApp number on the session. The form's phone is stored on the address, not copied into `email`. |

`product_option` and `quantity` are stored as text and sent to TiQR as integers.

```json
{
  "name": "{{customer_name}}",
  "address_line_1": "{{address_line_one}}",
  "address_line_2": "{{address_line_two}}",
  "city": "{{city}}",
  "state": "{{state}}",
  "country": "{{country}}",
  "pincode": "{{pincode}}",
  "email": "{{customer_email}}",
  "phone_number": "{{customer_phone}}",
  "phone": "{{customer_phone}}",
  "latitude": "{{delivery_latitude}}",
  "longitude": "{{delivery_longitude}}"
}
```

The WhatsApp Flow has to submit those field names. The Email input must be an email address. `email` is required to create the order. Guest checkout also needs `email` on the address. If the address omits it, the order email is copied onto the address. For delivery, `latitude` and `longitude` on the address are the stored pin, rounded to 6 decimal places. Location-based stores require that pin on the address to confirm the order.

There is no second confirmation step. A successful create sends an order-placed message (order number, delivery fee, and total when present). When the response includes a payment URL, that message is a WhatsApp **Pay now** CTA URL button so the shopper can complete payment. The flow then ends. If create fails because customer details are missing, the recover role asks for every missing field from the error, one reply at a time, in this order: name, phone, email, address line 1, address line 2, city, state, country, pincode, notes. `create_order` is retried only after all of those replies are saved on the session, with the same cart. The number of retries after the first attempt is `[codedflow] order_retries` (default 2). Other failures get a short apology with no API details.

```text
Order placed! Your order number is TQ-1.
Total: ₹40.00
[Pay now]
```

### Order status

**Check order status** calls TiQR MCP `lookup_order_status` for the WhatsApp number. It does not ask for an order id.

| Result | Message |
| --- | --- |
| Order found | `Order {display_uid} is {status}.` Underscores in the status become spaces, and the status is lowercased. Example: `Order ST-1 is confirmed.` |
| No display id | `Your latest order status is {status}.` |
| Nothing found, or the lookup fails | `I couldn't find a recent order for this phone number.` |

The flow ends after that message. This path does not attach a payment link. Payment retry stays on the separate commerce checkout path.

### Agent handoff

**Talk to agent**, an off-script reply the AI will not handle, and an AI error all end the same way. The customer is told a team member will help, an agent transfer is created, and the coded flow session is completed.

### Session values

These are the values later messages and the order payload read back.

| Key | Set when |
| --- | --- |
| `phone_number` | Every turn, from the session |
| `contact_name` | Every turn, from the contact profile |
| `customer_language` | Once, from the trigger message |
| `store` | `get_store` succeeds |
| `collections` | `list_collections` returns rows |
| `delivery_mode` | Fulfillment resolves pickup or delivery |
| `delivery_latitude`, `delivery_longitude` | A delivery pin is accepted |
| `delivery_zone`, `shipping_fee_paise` | Delivery eligibility succeeds |
| `collection_id`, `collection_name` | A collection row is chosen |
| `products` | `list_products` returns rows |
| `product_id`, `product_name`, `options`, `product_selected` | A product card is chosen |
| `option_id`, `option_name` | An option is selected |
| `quantity` | A whole number is accepted |
| `commerce_captured_fields`, `commerce_capture_labels` | A required collection field is answered while adding an option |
| `tiqr_cart`, `cart_count` | A line is appended. The line can include `product_name`, `option_name`, `capture_fields`, `capture_labels`, and `capture_order` |
| `customer_name`, `customer_email`, `customer_phone`, address fields, `customer_notes` | The WhatsApp Flow is submitted, using the form's own field names. A failed `create_order` can also fill any of these that the error said were missing |
| `order` | `create_order` succeeds |

## Where the code lives

| File | Role |
| --- | --- |
| `internal/handlers/codedflow/` | Engine package (`Host`/`Chat`, `Conv`, AI, intent, recover, preview sink, `Register`/`Run`) |
| `internal/handlers/codedflow_host.go` | Handlers adapter: `*App` as `Host`, `codedChat` as `Chat` |
| `internal/handlers/codedflow_run.go` | Resume / trigger wrappers calling `codedflow.Run` |
| `internal/handlers/codedflow_api.go` | List and keyword binding |
| `internal/handlers/codedflow_preview.go` | HTTP preview + Redis/DB preview helpers |
| `internal/handlers/tiqrecommerce/` | TiQR Ecommerce coded flow (`codedflow.Register` in `init`) |
| `internal/handlers/chatbot_processor.go` | Resume and trigger, ahead of visual flows |

A new flow is a `CodedFlow` value passed to `codedflow.Register` from `init`. It needs a unique `Key`, a `Name`, a `Description`, the outline `Steps`, and a `run` function. The admin UI picks it up from the binary. There is no API to create or delete the definition.
